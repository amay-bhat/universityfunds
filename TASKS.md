**2026-07-24 — Task 1.2 (seed script) complete.**
- `scripts/seed.ts`, run by `npm run seed`. Two design decisions worth carrying forward:
  - **Validate everything, then write — or write nothing.** All files are parsed and checked before the DB module is even imported, and the script exits 1 with the full error list on any failure. The Neon HTTP driver can't do interactive multi-statement transactions, so an all-or-nothing gate *before* the first write is the only way to guarantee a bad edit can't leave the DB half-updated.
  - **Upsert on natural keys + prune.** Rows are upserted (ids stay stable across re-seeds), and any DB row whose natural key is no longer in `data/` is deleted. Without the prune, deleting a row from a seed file would silently leave it live in the DB, which contradicts "seed files are the source of truth." Prune order is facts → upsert dims → upsert facts → prune dims, so FKs hold at every step.
- Validation covers: JSON shape and field types; `schools.json` ⟷ `SCHOOL_IDS` agreement in both directions (keeps the app's typed `SchoolId` from drifting from the data); enum membership for `category`/`series`/`documentType`; fiscal-year range; `pct` 0–100; `returnPct` within (-100, 200]; non-negative market values; duplicates on every key the DB uniquely constrains; **every `sourceId` resolving to `sources.json`** (PRD rule 2, mechanically enforced); and **allocations summing to 100% ± 1.0pp**.
- Tolerance choice: `ALLOCATION_SUM_TOLERANCE_PCT = 1.0`. Published allocation tables are rounded so exact 100 is rare, but ±1pp is tight enough to catch a genuinely dropped or double-counted line item. If a correctly-transcribed real report lands outside it during 1.3–1.6, widen the constant and note why here — don't nudge a number to fit.
- Two warnings (non-blocking, by design): a category used in allocations with no proxy mapping yet (expected until 1.7), and a source nobody cites (dead weight on the task-6.1 Methodology page).
- `--dry-run` (validate only, no DB, works without `DATABASE_URL`) and `--data-dir <path>` (point at another folder). `--data-dir` is what makes the "validation actually rejects a bad row" check testable without touching real data — fixtures live outside the repo, so there are no throwaway files in git.
- Verified: clean run on the current empty files (5 schools upserted; second run idempotent); a bad fixture produced 14 distinct errors (bad enum values, duplicates, out-of-range numbers, wrong types, missing field, dangling citation, 90% allocation sum) with exit 1 and the DB confirmed untouched; a good fixture summing to exactly 100.0 passed. `npm run lint` and `npm run build` both clean.
- Environment gotchas for future sessions: (1) `package.json` has no `"type": "module"`, so tsx compiles scripts as CJS and **top-level `await` fails** — wrap in an `async function main()`. (2) The `@neondatabase/serverless` client only accepts tagged-template calls; for a dynamically-built query string use `sql.query(text)`. (3) `tsconfig.json` includes `**/*.ts`, so `scripts/` is type-checked by `next build` — a type error there breaks the Vercel deploy.

**2026-07-24 — `[PROXY DECISION]` Yale FY2021–FY2025 allocation coverage. Answered by Fable; implemented by Opus. Closes the open decision from task 1.3.**
- **Question:** Yale published allocation percentages through FY2020 and then stopped. How should FY2021–FY2025 be handled, and what is the project-wide rule for tasks 1.5–1.6?
- **Options weighed:** (A) leave the gap, allocation series ends FY2020, coverage end labelled at every point of display; (B) derive FY2021–FY2025 from the financial report's NAV tables normalized to the NAV subtotal, marked as derived; (C) *reconciled* derivation validated against the overlap years before being trusted; (D) ask Yale.
- **Opus (child) recommended A**, on the grounds that a chart splicing two measurement bases is what Article 4 exists to prevent.
- **Fable (parent) independently recommended A as well, adopted project-wide, plus two additions** — and materially strengthened the reasoning. Fable's decision governs.
- **Why B is rejected outright rather than caveated — the part Opus got wrong.** Opus framed B as a *disclosure* problem. It is a *distortion* problem. The NAV subtotal excludes cash and directly-held fixed income (~7.5% of FY2024: $41.3B total vs. $38.2B subtotal), so normalizing to it drives `fixed_income_cash` toward zero and inflates every risk-asset category ~8% relative. The Translator would hand a DIY investor a "Yale copycat" with essentially no bonds, for a school whose own policy holds roughly 30% in market-insensitive assets. A caveat cannot repair a number that points the wrong way. Fable also identified a basis mismatch reconciliation may never cure: the report percentages are **economic exposure including leverage** — which is exactly why Yale reports negative Cash weights in FY2008/09/11 — while NAV tables are accounting values.
