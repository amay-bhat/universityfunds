Endowment Investing Tool — Project Plan

A free web app that shows everyday investors how famous university endowments invest, and what a buy-it-yourself version of those strategies looks like.

Drafted July 23, 2026 · Status: planning docs written (PRD.md, TASKS.md, CLAUDE.md) — ready for human review, then build

What We're Building

An open-to-anyone website (no accounts, no sign-up) where a curious DIY investor can explore how the most famous university endowments — Yale, Harvard, Stanford, MIT, Princeton — have invested over the decades, see that strategy translated into normal funds anyone can buy, and compare it honestly against simple index investing.

It is an education tool, not financial advice: it never tailors anything to an individual's money, which keeps it useful, fast to build, and safely on the right side of the line.

Decisions Made (Brainstorm Summary)

  1. Audience: everyday DIY investors
    People managing their own retirement or brokerage accounts who are curious how the pros invest.
  2. Core experience: all three features, kept thin
    A history explorer (allocations and returns decade by decade), a "copy the pros" translator (the strategy rebuilt with ordinary funds), and head-to-head comparisons (endowment style vs. simple indexing). Usage tells us which to deepen later.
  3. Schools: 5–6 famous ones, deep history
    Yale, Harvard, Stanford, MIT, Princeton, possibly one more. Depth beats breadth; more schools can come later.
  4. Personal-ness: look, don't touch
    No accounts, no personalization, nothing tailored to a specific person's finances. Education, not advice.
  5. Goal: portfolio piece / learning project
    Ship free, fast, and public. If people love it, that's validation to build on.
  6. Data: hand-curated dataset
    Numbers typed from annual reports and industry studies into clean seed files in the repo, every figure with a cited source, updated yearly. A seed script loads them into the database. No scraping, no live market feeds in v1.
  7. Tech: Next.js on Vercel, Neon database
    A Next.js web app with interactive charts, hosted on Vercel (Pro plan), using Vercel-native components wherever possible. Neon Postgres holds the dataset via Vercel's native integration.

How We'll Build It: The "Docs Conduct" Workflow (Option B)

No model acts as an always-on manager. Instead, the planning documents in the repo hold the plan and the current state, and each AI model is brought in only for the work it's best at. The human presses the switch between them — which costs nothing.

ModelRoleWhen It Runs
Fable 5 Planner & reviewer. Writes the PRD, task breakdown, and handoff notes; later reviews finished phases, adjusts the plan, and unblocks anything hard. Short, focused sessions at decision points only.
Sonnet 5 Builder. Picks up one task at a time from the task list, reads the planning docs for context, builds, checks the task off. The bulk of all sessions — the workhorse.
Opus Bench player. Called in only if a specific problem proves genuinely hard (most likely candidate: the copycat-portfolio math). Rarely, if ever.
Why this saves tokens: a standing conductor re-reads the entire growing conversation on every turn, so the priciest model becomes the highest-volume one. With the plan living in files instead, any fresh cheap session can read the docs and know everything — no history to drag around, no context to re-explain.

The Session Protocol

  1. Fable session (short) — planning. Write three documents into the repo: the lean PRD, the task checklist (each task small and self-contained), and handoff notes (CLAUDE.md) so any fresh session can pick up cold. Done July 23, 2026.
  2. Switch to Sonnet, fresh session — building. "Read the docs, do task 1." Then task 2, task 3, and so on — clearing the conversation between tasks so history never bloats. ← Next, after human review of the docs.
  3. Checkpoint — switch back to Fable (short). When a phase completes or Sonnet gets stuck: Fable reads the docs and the code, reviews the work, updates the plan, and hands back.
  4. Repeat steps 2–3 until v1 ships.

Working Rules

  • Every task must be written so a fresh session with zero conversation history can complete it from the docs alone.
  • Builder sessions update the task checklist as they finish, so the docs always reflect true state.
  • Keep Fable sessions short and purposeful: review, decide, update docs, hand off.
  • Don't reach for Opus preemptively — only when Sonnet has actually struggled with a specific problem.
  • The dataset is the project's foundation: every number gets a cited source before it enters a data file.
  • All copy stays educational in tone — the tool describes history and mechanics, never tells anyone what to do with their money.
